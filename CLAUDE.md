## Architecture

**This app is local-first: there is no server-side database.** Every visitor's data (games, reviews, codebooks, codes, taggings) lives entirely in their own browser via [PGlite](https://pglite.dev/) (Postgres compiled to WebAssembly), persisted to IndexedDB. Vercel only serves the app shell and proxies the two things that need a server-held secret (OpenAI, Steam ingestion). Read README.md's "Architecture: local-first" section for the full reasoning before assuming a server DB exists.

- `prisma/schema.prisma` and `prisma/migrations/` are **documentation only** — never executed. The real runtime schema is `public/localdb/schema.sql`, applied by PGlite itself in the browser on first load. Don't reach for `DATABASE_URL` or `prisma migrate`; there isn't one.
- **Data access**: `src/lib/localDb/client.ts` exports `getDb()`, a module-level singleton `Promise<PGlite>` (dynamically imported so its ~5MB WASM assets never enter the server bundle). All queries live in `src/lib/localDb/queries/*.ts`, one file per resource, hand-written parameterized SQL ported 1:1 from the schema's shape — no ORM at runtime.
- **First-visit seeding**: a brand-new browser loads `public/localdb/seed.tar.gz` (a real worked example) instead of an empty schema. This decision has to happen *before* constructing PGlite, since `loadDataDir` is constructor-only — see the `isFirstVisit`/`hasExistingLocalDatabase` logic in `client.ts`.
- **Save/Open project file** (`src/lib/localDb/projectFile.ts`) wraps PGlite's `dumpDataDir()`/`loadDataDir` for a portable `.tar.gz` export/import of the whole local database. Gotcha: PGlite refuses `loadDataDir` if the target database already has data (`"Database already exists, cannot load from tarball"`) — `resetDbFromFile` in `client.ts` explicitly deletes the underlying IndexedDB store first, and nulls the singleton *before* that delete so a failed import can't leave later queries pointed at a closed connection.
- **API routes are all thin, stateless proxies** (7 total, under `src/app/api/`): `reviews/[reviewId]/suggest-codes` and `games|projects/[id]/suggest-codebook` (both variants share one handler, `src/lib/api/suggestCodebookHandler.ts`) are OpenAI proxies — the client already has the relevant data locally and sends it in the request body; the route's only job is the OpenAI call. `games/[gameId]/ingest` streams newline-delimited JSON progress events while it pages through Steam's `ajaxappreviews` endpoint server-side (a browser fetch to Steam directly would hit CORS/rate-limit issues) but does no DB writes — the client performs the local upsert as it reads the stream (see `src/lib/ingestClient.ts`); `games/[gameId]/review-count` is the same Steam-proxy idea but a single `num_per_page=1` request, used to show "N reviews on Steam" before/during a run rather than to actually ingest anything. `rate-limit-status` and `auto-code-batch-size` are non-consuming peeks that expose server-only env config (rate-limit quota, the Train & Auto-Code bulk-coding batch size) to the client, the same way: a plain env var isn't visible to the browser bundle without a route like this.
- **Rate limiting** (`src/lib/rateLimit.ts`): Upstash Redis via Vercel's KV storage integration — env vars are `KV_REST_API_URL`/`KV_REST_API_TOKEN` (Vercel's dashboard naming, not Upstash's own `UPSTASH_*`, though both are checked). `RATE_LIMIT_BUCKETS` is the single source of truth for both enforcement (`checkRateLimit`, used by the AI routes) and the non-consuming client-facing peek (`peekRateLimit`, backing `rate-limit-status`) — keep them reading from the same config so they can't drift. Gracefully no-ops when the env vars are absent (local dev has no rate limiting by default).
- **Active-codebook navigation** (`src/lib/activeCodebook.ts` + `src/components/CodebookToolbar.tsx`): a codebook is the unit Analytics/export are scoped to — different codebooks can define incompatible codesets, so there's no "all codebooks" aggregate view. "Active codebook" resolves URL param → `localStorage` (per game/project) → first-in-list, threaded via a shared `?codebookId=` param across the Reviews list, a review's tagging view, and Analytics so it's one persistent selection rather than re-picked per page. Tagging queries (`listTaggingsForReview`, `countCodedReviews`, `listReviews`) take a `codebookId` to scope what's shown/counted to the active codebook only — a review can technically carry taggings from multiple codebooks, but the UI only ever shows the active one's.
- **`Coder` table design**: one table with a `kind: HUMAN | AI` field, not a separate human/AI concept — every `Tagging` has a real FK to a `Coder` row regardless of kind. This is what makes the Cohen's kappa computation (`src/lib/kappa.ts`) a simple group-by rather than a join across different shapes.
- **Game- vs project-scoped duplication is deliberate.** A `Project` groups several `Game`s so one codebook can analyze across all of them (`Codebook.gameId` XOR `Codebook.projectId` — a DB check constraint enforces exactly one is set). This means most review/codebook/training pages exist twice, nearly identically, under `src/app/games/[gameId]/...` and `src/app/projects/[projectId]/...` (e.g. `CodebookPromptEditor.tsx`, `TrainingBucketPanel.tsx`, and `AutoCodeRestPanel.tsx` live only under the `games/` tree and are imported directly into the `projects/` pages rather than duplicated). When fixing a bug or adding a feature to one, check whether the other scope needs the identical change — the project owner expects both to stay in sync.
- **Codebooks are versioned by copying forward, not edited in place.** "Revise codebook" (`reviseCodebook` in `src/lib/localDb/queries/codebooks.ts`) creates a new `Codebook` row with `version` incremented and `previousVersionId` set, copying codes and (if set) the per-codebook `promptOverride` and `trainingId` forward; the old version's codes/taggings/disagreements are untouched and independent.
- **Per-codebook AI prompt override**: `Codebook.promptOverride` (nullable; null = use the shared `DEFAULT_SUGGEST_CODES_SYSTEM_PROMPT` in `src/lib/prompts.ts`) lets a researcher edit the exact system prompt sent to `suggest-codes` for that codebook, edited through the `CodebookPromptEditor` component and sent by the client in every suggestion request (the route itself has no DB access to look it up server-side).
- **Train & Auto-Code pipeline** (`CodebookTraining`, `ReviewSplitAssignment`, `AutoCodeAttempt`; query logic in `src/lib/localDb/queries/training.ts`): a researcher can draw a one-time random split of a codebook's reviews into calibration/test/verification buckets, blind-hand-code them, then run the AI independently over the same reviews (no accept/reject step) to measure agreement via Cohen's kappa before trusting it on the rest of the corpus. `CodebookTraining.phase` moves forward only (`calibrating → testing → locked → verified`) — locking a training blocks further edits to that codebook's codes/prompt (`CodebookLockedError`), and once `verified`, held-out reviews rejoin normal browsing and an "auto-code the rest" action bulk-codes everything else unsupervised, batched and resumable via `AutoCodeAttempt`.
- **Review relevance vs. deletion are different, deliberately.** `ReviewRelevance` is a per-codebook (not global, not per-game) "exclude this review" mark — reversible, scoped to one codebook's research question, and distinct from actually deleting a `Review` row (which cascades through its taggings and is permanent). A review can be irrelevant to one codebook and perfectly fine for another on the same game.
- **A review's text can be edited in place** (`updateReviewText`/`revertReviewToOriginal` in `src/lib/localDb/queries/reviews.ts`): the original is preserved in `Review.originalText` on first edit (its presence is the "edited" flag, no separate boolean), and the ingest upsert's `ON CONFLICT` clause skips refreshing `text`/`textLength` for an edited review so a later "Sync more reviews" can't silently clobber the edit. Only `text` is editable — other fields feed filtering/sampling/training stratification, so letting them drift from Steam's real data would be worse than useless.
- **Schema changes touch three files, always**: `public/localdb/schema.sql` (the real runtime DDL), `src/lib/localDb/client.ts`'s `runMigrations` (an idempotent `columnExists`/`tableExists`-gated `ALTER`/`CREATE`, since this runs unconditionally on every connect — fresh bootstrap, loaded dump, or an existing browser alike — not just once), and `prisma/schema.prisma` (documentation only, mirrors the other two but is never executed). Skipping the migration step means an already-provisioned browser (anyone who's visited before, or the live seed) never picks up the change.

**Git branches**: `main` is the current local-first app. `initial-prototype` preserves the original server-hosted Prisma+Postgres version for historical reference — not maintained, don't merge into it.

**Deployment**: Vercel project `arianniakans-projects/steam-review-coding-tool`, auto-deploying from GitHub pushes to `main`. PGlite/WASM bundling and rate-limiting both behave differently there than under `next dev` (rate limiting no-ops locally without the KV env vars set) — verify any deploy-affecting change against the live URL, not just local dev.
